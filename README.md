# Jiho Kim Skills

AI 에이전트와 일할 때 쓰는 행동 지침. [andrej-karpathy-skills](https://github.com/forrestchang/andrej-karpathy-skills)와 같은 구조의 `CLAUDE.md` 하나다.

한국어 | [English](./README.en.md)

## 왜 만들었나

AI를 많이 쓰지만 결과가 항상 좋지는 않다. 원인은 세 가지다.

- **주도권이 AI 쪽으로 넘어간다.** 확률 모델이라 AI가 방향을 쥐면 결과 품질이 매번 달라진다.
- **부분만 본다.** 지금 고치는 곳만 보다가 전체 맥락을 잃는다.
- **복잡도가 오른다.** 문제를 덧붙여서 풀다가 원래 풀려던 문제에서 멀어진다.

그래서 원칙은 셋이다. **방향은 사용자가 정한다. 전체 맥락을 지킨다. 복잡도는 예산이다.**

## 날카로운 기준

정해진 순간에 예/아니오로 답하는 시험 10개. 실패하면 오른쪽 행동을 먼저 한다. ★는 "예"가 실패다.

| 순간 | 시험 | 실패하면 |
|---|---|---|
| 시작 전 | 목표, 완료 기준, 기준선, 범위를 각각 한 문장으로 말할 수 있는가? | 한 번에 하나씩 묻는다 |
| 바꾸기 전 | 이 변경 뒤에도 앞서 정한 것이 모두 그대로인가? | 전체를 바꾸기 전에 묻는다 |
| 바꾼 뒤 | ★ 규칙, 예외, 옵션, 코드 경로의 수가 늘었는가? | 무언가를 빼는 안을 찾는다 |
| 고침이 실패한 뒤 | ★ 같은 문제에서 두 번째 실패인가? | 멈추고 전제를 시험한다 |
| 지적받은 뒤 | 지적 뒤의 원칙을 말하고, 확인한 곳을 전부 댈 수 있는가? | 고치기 전에 전수 조사한다 |
| 코드를 쓸 때 | ★ 같은 사실이나 계산이 두 곳에 생겼는가? | 주인 하나를 정한다 |
| 코드를 쓸 때 | 처음 보는 사람이 구조만 보고 이 변경의 자리를 찾을 수 있는가? | 제자리로 옮긴다 |
| 커밋 전 | 바뀐 줄이 모두 요청으로 설명되는가? | 그 줄을 뺀다 |
| 완료라고 하기 전 | 모든 주장이 직접 돌려 보거나 본 것에 근거하는가? | 확인하거나, 확인 못 했다고 쓴다 |
| 답하기 전 | ★ 사용자가 "이게 무슨 말이야?"라고 물어야 하는가? | 다시 쓴다 |

## 다섯 원칙

**1. 시작 전에 빈 칸을 없앤다.** 결정은 사용자의 것, 사실은 AI가 찾는다. 목표, 완료 기준, 기준선, 범위 중 하나라도 비면 묻는다. 한 번에 하나씩 객관식으로, 추천과 이유를 붙여서. 답이 모호하면 빈 칸이 없어질 때까지 다시 묻는다. 찾아볼 수 있는 것은 묻지 않는다.

**2. 부분을 고치고, 전체는 지킨다.** 부분을 전체에 맞추고, 전체를 부분에 맞추지 않는다. 개념이나 구조가 바뀌면 설계 먼저, 보이는 것이 바뀌면 샘플 먼저. 전체를 꼭 바꿔야 하면 이유와 영향 범위를 보여 주고 묻는다.

**3. 복잡도는 예산이다.** 덧붙이기 전에 뺀다. 한 규칙에 예외가 셋이면 규칙이 틀린 것이다. 같은 문제를 두 번 고쳐도 안 되면 멈춘다. 새것은 옛것을 대체하고, 둘을 같이 두는 건 승인과 끝낼 날짜가 있을 때만이다.

**4. 지적 하나는 패턴이다.** 지적을 사례 하나가 아니라 깨진 원칙으로 본다. 같은 패턴을 전부 찾고 근본을 고친다. 단 같은 문제만 고치고, 다른 문제는 보고만 한다. 같은 실수가 두 번이면 글보다 강한 장치(구조, 타입, 검사, 테스트)로 막는다.

**5. 완료는 확인한 결과다.** 처음 쓰는 사람처럼 직접 써 본다. 돌려 보지 않은 것은 주장하지 않는다.

**대화할 때:** 묻는 말에 먼저, 사용자의 언어로, 쉬운 말로 답한다. 말보다 바뀌는 부분만 그린 샘플로 보여 준다. "좋네"는 확정이 아니다. 상태는 확인함 / 확인 못함 / 남음으로 보고한다.

**코드를 쓸 때:** 덧대지 않고 설계를 지킨다. 역할은 MECE로 나누고, 사실 하나에 주인 하나, 의존은 한 방향. 새 기능은 기존 구조의 제자리에 넣고, 안 맞으면 구조 변경을 제안한다. 상태를 바꾸는 일은 두 번 돌거나 중간에 죽어도 안전해야 한다.

전문은 [CLAUDE.md](./CLAUDE.md), 전/후 예시는 [EXAMPLES.md](./EXAMPLES.md).

## 카파시 지침과 다른 점

| 카파시 | 여기 |
|---|---|
| Think Before Coding | 원칙 1, 2. 가정을 말하는 데서 그치지 않고 빈 칸이 없어질 때까지 묻는다. 부분을 고쳐도 전체를 지킨다 |
| Simplicity First | 원칙 3. 같은 방향에 두 번 실패하면 멈추기와 대체 규칙을 더했다 |
| **Surgical Changes** | **원칙 4. 반대.** 지적 하나를 같은 패턴 전체로 넓힌다. 단 같은 문제만 |
| Goal-Driven Execution | 원칙 5. 실제 사용자처럼 써 보고, 확인 못 한 것을 따로 보고한다 |
| (없음) | 날카로운 기준 10개, 코드 설계 규칙 |

둘을 함께 쓰면 원칙 4가 충돌한다. 이쪽이 우선한다.

## 출처

실제 AI 작업 세션 600여 개에서 사용자가 반복해 요구한 것과, 실제 프로젝트의 작업 가이드를 일반화했다.

## 설치

Claude Code 플러그인:
```
/plugin marketplace add SteveKim0513/jiho-kim-skills
/plugin install jiho-kim-skills@jiho-kim-skills
```

플러그인 스킬은 Claude가 설명문을 보고 불러오는 방식이라 항상 켜지지는 않는다. 항상 적용하려면 `CLAUDE.md`를 프로젝트에 두거나 `~/.claude/CLAUDE.md`에 붙인다.

```bash
curl https://raw.githubusercontent.com/SteveKim0513/jiho-kim-skills/main/CLAUDE.md >> ~/.claude/CLAUDE.md
```

Cursor는 `.cursor/rules/jiho-kim-guidelines.mdc`가 항상 적용된다. 자세한 건 [CURSOR.md](./CURSOR.md).

## 요청하는 사람을 위한 틀

원칙 1은 AI가 빈 칸을 묻게 하지만, 첫 메시지에 직접 주면 더 빠르다.

```
목표: (한 문장)
완료 기준: (확인할 수 있는 한 문장)
기준선: (맞출 기존 결과물, 없으면 "없음")
범위: (어디까지 할지. 예: 로컬 확인까지 / PR까지 / 배포까지)
```
