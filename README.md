# Jiho Kim Skills: 내가 AI와 일하는 방식

[forrestchang/andrej-karpathy-skills](https://github.com/forrestchang/andrej-karpathy-skills)와 같은 구조의 `CLAUDE.md` 하나. 카파시 지침은 LLM이 흔히 하는 실수에서 출발했고, 이 저장소는 **한 사람이 실제로 AI를 쓴 기록**에서 출발했다.

한국어 | [English](./README.en.md)

## 근거

직접 쓴 세션 615개, 메시지 5,855개(2025-09-11 ~ 2025-10-23)를 8개 구간으로 나눠 전부 읽고 반복되는 요구와 다시 작업의 원인을 셌다.

| 수치 | 뜻 |
|---|---|
| 메시지의 44%가 15자 이하 | 짧은 지시가 기본이다. AI가 범위를 짐작하면 틀린다 |
| 세션 37%(230개)가 "배포"류 한 단어로 시작 | 한 단어 지시의 기본 범위를 미리 정해 둬야 한다 |
| "기획 먼저" 요구가 30개 세션 이상 | 구현보다 기획이 먼저다 |
| "한글" 한 단어 답장이 30개 세션 이상 | 영어로 답하면 다시 작업이다 |
| "좁게 해석하지 말고 전체 재검토" 요구가 구간마다 8~11개 세션 | 지적 하나는 원칙 위반의 신호다 |

한 줄 요약: **AI에게는 "기획 먼저, 단순하게, 전체를 근본부터, 직접 확인"을 요구하는 꼼꼼한 총괄.** 정작 본인은 기준을 늦게 말하고 한 단어로 지시해서, 그게 다시 작업의 가장 큰 원인이 된다. 그래서 이 지침은 AI 쪽 규칙(1~5)에 더해 **그 빈틈을 AI가 메우는 규칙(0)**을 앞에 둔다.

## 카파시 지침과 다른 점

| 카파시 | 이 저장소 | 왜 |
|---|---|---|
| Think Before Coding | 1. 기획하고, 보여 주고, 고르게 한다 | 가정을 말하는 데서 멈추지 않고, 객관식과 샘플 화면으로 보여 준다 |
| Simplicity First | 2. 단순하게, 빼는 쪽으로 | 같은 방향. 단, 기존 기능 삭제는 먼저 묻는다 |
| **Surgical Changes** | **3. 전체를 근본부터 고친다** | **정반대.** 지적 하나를 사례 하나로 보지 않고 같은 패턴을 전수 조사한다. 경계: 같은 문제는 전체, 다른 문제는 보고만 |
| Goal-Driven Execution | 4. 직접 써 보고 증명한다 | 테스트 통과에 더해 실제 사용자처럼 써 본다. "다 됐어?"에 답하는 형식을 고정한다 |
| (없음) | 0. 시작 전에 범위와 기준을 잡는다 | 사용자가 기준을 늦게 말하는 습관을 AI가 보완한다 |
| (없음) | 5. 병렬 세션 안전 | 여러 세션이 같은 저장소를 고칠 때 생기는 충돌을 막는다 |

두 지침을 함께 설치하면 원칙 3이 충돌한다. **이 저장소의 3이 우선한다.** 카파시 3의 "다른 문제는 건드리지 않는다"는 그대로 살아 있다.

## 여섯 원칙

### 0. 시작 전에 범위와 기준을 잡는다

**짧은 지시를 짐작으로 채우지 않는다.**

- 완료 기준이 없으면 한 줄로 제안하고 확인받은 뒤 시작한다. "완벽하게", "끝까지"는 기준이 아니다.
- 한 단어 지시("진행해", "배포", "정리해", "고쳐", "한글")의 기본 범위를 표로 정해 둔다. 되돌리기 어려운 일은 "네", "진행해"로 하지 않는다.
- 세션에서 정한 것을 결정 목록으로 유지한다. 새 요청이 이전 결정과 어긋나면 한 줄로 알린다. 막는 게 아니라 비용을 보이게 하는 것이다.

### 1. 만들기 전에 기획하고, 보여 주고, 고르게 한다

**짐작해서 구현하지 않는다. 사용자가 낸 안보다 나은 안을 가져온다.**

- 구현 전에 기획. 결정할 일은 객관식으로, 추천과 이유를 붙여서.
- 말보다 로컬 웹이나 샘플 화면으로. 전체를 띄우지 않고 고칠 부분만.
- 쉬운 한국어로, 묻는 말에 먼저 답한다.

**점검:** 내 답을 다시 붙여 넣고 "무슨 말이야?"라고 물을 것 같은가?

### 2. 단순하게, 빼는 쪽으로

**문제가 생기면 덧붙이지 않고 덜어 낸다.**

- 쓸모가 불분명한 기능은 남기지 않는다. 규칙과 예외를 늘리지 않는다.
- 시키지 않은 것은 넣지 않는다. 정한 것을 바꾸지 않는다.
- 기존 기능을 지울 때는 먼저 묻는다.

**점검:** 이번 변경으로 원칙이나 예외가 하나 늘었는가?

### 3. 하나를 지적받으면 전체를 근본부터 고친다

**지적 하나는 사례 하나가 아니라 원칙 위반의 신호다.**

- 같은 논리로 전수 조사한다. 땜질하지 않고 근본 원인을 고친다.
- 특정 사례에 맞추지 않는다. 기존 체계를 기준선으로 삼고, 새 기능은 옛 기능을 대체하거나 통합한다.
- 한 번 한 실수는 가이드, 훅, 문서로 남긴다.

**점검:** 같은 문제가 있는 다른 곳에도 적용됐는가? 재발을 막을 장치가 남았는가?

### 4. 직접 써 보고, 끝났다는 걸 증명한다

**"완료"는 말이 아니라 확인한 결과다.**

- 실제 사용자처럼 직접 써 본다. 확인하지 않은 주장은 하지 않는다.
- 효과가 확인되지 않은 변경은 되돌린다.
- "다 됐어?"에는 `확인함 / 확인 못함 / 남음` 형식으로 답한다.

**점검:** "남은 일은?"에 확인한 증거로 답할 수 있는가?

### 5. 여러 세션이 같은 저장소를 고친다

**내가 만들지 않은 변경은 남의 것이다.**

- 고치기 전에 `git status`를 본다. 남의 변경이 있으면 알리고 피해서 작업한다.
- 메시지가 이 프로젝트와 무관해 보이면 한 줄만 묻고 기다린다.

전문은 [CLAUDE.md](./CLAUDE.md), 실제 대화 기반 예시는 [EXAMPLES.md](./EXAMPLES.md).

## 거울: 요청하는 사람의 체크리스트

위 원칙을 AI에게 요구하면서 내 요청에는 빠져 있던 것들이다. 다시 작업의 원인이 분명히 사용자 쪽인 경우만 셌다. 원칙 0은 이걸 AI가 보완하는 장치지만, 첫 메시지에서 내가 직접 주면 더 빠르다.

| 내 습관 | 실제로 생긴 일 | 첫 메시지에 넣을 것 |
|---|---|---|
| 기준을 결과 본 뒤에 말한다 | "베싸 수준으로", "유튜브는 레드, 카톡은 노랑", "생성 메뉴가 맨 위"가 다 나중에 나왔다 | **완료 기준 한 줄**과 기준선 |
| 진행 중에 목표와 구조를 바꾼다 | 메시지 시스템 구조 4번 변경, CI를 GitHub Actions → CircleCI → 결제로 왕복, 검사 체계를 만들고 전부 삭제("4시간을 여기에 쓴 게 말이 되냐") | 바꾸기 전에 "이전 결정 취소"라고 한 줄 |
| "완벽하게, 끝까지"에 기준이 없다 | 밤새 "완벽히 연동" → 다음 날 "끊긴 지점이 너무 많아 운영에 쓸 수 없어" | 측정할 수 있는 기준. 예: "가입→결제 1회 통과" |
| 한 단어로 지시한다 | "진행해"에 AI가 배포까지 했다. "정리해"에 AI가 숨길지 지울지 물었지만 답하지 않았다 | 어디까지인지: 로컬 확정 / PR / 배포 |
| 세션을 여러 개 병렬로 돈다 | 엉뚱한 세션에 메시지 6건 이상, 75개 파일 git 충돌, 내가 세션 사이 중계자가 됐다 | 세션마다 맡는 저장소와 범위를 하나로 |

### 첫 메시지 틀

```
목표: (한 문장)
완료 기준: (확인할 수 있는 한 문장)
기준선: (맞출 기존 서비스나 UI, 없으면 "없음")
범위: 로컬 확정 / PR까지 / 배포까지
```

좋은 신호: 10월 22일부터 "deeper, not bigger"를 붙이고 성공 기준부터 정하는 요청이 나오기 시작했다.

## 설치

**A. Claude Code 플러그인 (권장)**

Claude Code 안에서 마켓플레이스를 추가하고:
```
/plugin marketplace add SteveKim0513/jiho-kim-skills
```

플러그인을 설치한다:
```
/plugin install jiho-kim-skills@jiho-kim-skills
```

모든 프로젝트에서 스킬로 쓸 수 있다.

**B. CLAUDE.md (프로젝트별)**

새 프로젝트:
```bash
curl -o CLAUDE.md https://raw.githubusercontent.com/SteveKim0513/jiho-kim-skills/main/CLAUDE.md
```

기존 프로젝트에 덧붙이기:
```bash
echo "" >> CLAUDE.md
curl https://raw.githubusercontent.com/SteveKim0513/jiho-kim-skills/main/CLAUDE.md >> CLAUDE.md
```

**C. 전역 적용**

모든 세션에 적용하려면 `~/.claude/CLAUDE.md`에 붙인다.

## Cursor에서 쓰기

[`.cursor/rules/jiho-kim-guidelines.mdc`](.cursor/rules/jiho-kim-guidelines.mdc)가 `alwaysApply: true`로 들어 있다. 다른 프로젝트에서 쓰는 법은 [CURSOR.md](./CURSOR.md).

## 파일 구성

```
CLAUDE.md                              # 지침 전문 (Claude Code 프로젝트용)
skills/jiho-kim-guidelines/SKILL.md    # 같은 내용, 플러그인 스킬
.cursor/rules/jiho-kim-guidelines.mdc  # 같은 내용, Cursor 규칙
.claude-plugin/                        # 플러그인·마켓플레이스 메타데이터
EXAMPLES.md                            # 실제 대화 기반 전/후 예시
CURSOR.md                              # Cursor 설정 안내
```

세 지침 파일의 본문은 항상 같아야 한다. 하나를 고치면 셋을 함께 고친다.

## 핵심

카파시는 "무엇을 할지 말하지 말고, 성공 기준을 주고 지켜보라"고 했다. 이 저장소는 거기에 하나를 더한다. **기준을 주지 않으면, AI가 먼저 기준을 물어야 한다.** 그게 다시 작업을 가장 많이 줄인다.
